## G3 — Empty dropdowns: full result

**Attributes with an empty `dropdown_options` AND no resolving source: NONE.**

Checked all 33 `dropdown` / `multi_select` registry docs. Every one either has a populated `dropdown_options` array or a `dropdown_source` / `enum_source` that resolves live.

**Appendix B's "`site_owner` is known" is incorrect** (Task C, C4): `attribute_registry/site_owner` has `dropdown_options: []` **but** `dropdown_source: "site_registry"`, which resolves to 3 active sites. `AttributeField.tsx:82-85` maps them and `:154-166` uses them. It is a correctly-configured registry-driven dropdown.

The three registry-driven dropdowns all resolve non-empty live: `site_registry` → 3 active · `brand_registry` → 41 active · `department_registry` → 5 active. All three also have an explicit `registryError === "empty"` disabled state ([AttributeField.tsx:101-103](frontend/src/components/AttributeField.tsx#L101-L103), `:152`), so an empty registry degrades visibly rather than silently — that part is well built.

**The real defect in this family is the opposite one:** `website` is a `multi_select` whose options are a **hardcoded literal list** rather than a registry read, and 4 of its 7 options (`fbrkclothing.com`, `plndr.com`, `shiekhshoes.com`, `trendswap.com`) are **inactive sites** an operator can still select. Filed as G3-1.
